# HSK 5급 데일리

HSK 3.0 5급 읽기와 쓰기를 평일에 10분쯤 연습하는 드릴. 혼자 쓰는 도구라 로그인도 서버도 없다.

한 세트는 단락 배열 5문항, 어순 배열 3문항, 단문 빈칸 2~3문항이고 월요일과 금요일 첫 세트에 쓰기 1문항이 붙는다.
결과 화면에서 한 세트 더 풀 수 있다. 하루에 몇 세트를 풀든 상관없다.

같은 문항은 두 번 나오지 않는다. 해설을 읽은 문항을 다시 푸는 것은 실력이 아니라 기억을 묻는 일이라서다.
대신 정답률이 낮은 어법이 붙은 문항을 앞으로 당긴다. 약한 자리를 같은 문장이 아니라 다른 문장으로 다시 만난다.

긴 지문은 세트와 따로 돈다. 세트를 하나도 풀지 않아도 머리의 긴 지문 단추로 바로 열 수 있고,
하루에 몇 편을 읽든 상관없다. 점수도 세트 점수와 섞지 않고 따로 적는다. 둘은 다른 것이라서다.

문제를 푸는 화면에는 한국어가 한 글자도 없다. 지문도 문항도 보기도 칸 이름도 단추도 전부 중국어다.
실제 시험지에 없는 것은 여기에도 없어야 한다. 쓰기도 마찬가지라 문제 번역과 쓸 만한 어휘는
채점 화면으로 옮겼다. 옆에 두면 그걸 보고 쓰게 되는데, 시험장에는 없는 것들이다.

한국어는 채점한 다음에 나온다. 해설은 보기 네 개가 각각 무슨 뜻인지 적고, 지문에서 가져갈 말을
여덟 개쯤 뽑아 둔다. 보기가 본문에 나온다 안 나온다 하는 말은 적지 않는다. 읽으나 마나 한 말이라서다.

쓴 글은 채점 화면에서 기계로 점검한다. 글자 수, 단락, 반각 문장부호, 글자 사이 띄어쓰기,
그리고 `data/wrules.json` 에 적어 둔 어법 규칙을 본다. 跑的快 는 跑得快 로, 二个 는 两个 로,
桌子们 은 桌子 로, 고친 모양까지 같이 보여 주고, 고칠 것을 전부 적용한 글을 아래에 한 번 더 둔다.
내용이 주제에 맞는지, 문장이 중국어답게 읽히는지는 이 점검이 보지 못한다. 화면에도 그렇게 적어 두었다.

문항은 단락 배열 46세트, 어순 배열 138문항, 빈칸 46지문, 쓰기 10문항, 긴 지문 20편이 있다.
세트로는 46세트, 채점되는 문항은 488개다. 하루 두 세트로 평일 23일 동안 같은 문항이 겹치지 않는다.

어순 배열은 받아들이는 배열이 여럿인 문항이 많다. 목적어를 화제로 앞에 낸 꼴, 부사어를 주어 앞으로 낸 꼴,
접속사 뒤에 주어를 넣은 꼴이 모두 맞는 중국어라서다. 토막을 한 칸 옮기거나 두 칸을 맞바꾼 배열 4,027가지를
전수로 훑어서 빠져 있던 29개를 채웠다. 맞는 답을 틀렸다고 채점하면 해설을 읽고도 납득할 수가 없다.

## 어디서 쓰나

https://tinykingdoms.github.io/hsk-daily/

폰에서는 크롬으로 그 주소를 열고 메뉴에서 홈 화면에 추가를 누른다.
앱처럼 깔리고 지하철에서도 열린다.

손에서 볼 때는 빌드 과정 없이 정적 파일을 그대로 띄우면 된다.

```bash
python -m http.server 8787
```

주소 끝에 `?d=2026-11-13` 을 붙이면 그 날짜의 세트를 볼 수 있다.

## 문항 고치기

문항은 `data/` 의 JSON 다섯 개에 들어 있다. 고친 뒤에는 반드시 검증을 돌린다.

```bash
python tools/check.py
```

폴더를 하나 넘기면 그 폴더만 본다. 새 문항을 합치기 전에 따로 돌려 볼 때 쓴다.

```bash
python tools/check.py ../staging
```

긴 지문의 보기는 정답만 길어지지 않게 맞춘다. 정답은 본문에서 가져오니 길고 오답은 지어내니 짧아지는데,
그대로 두면 본문을 읽지 않고 제일 긴 것을 골라도 맞는다. 처음 올린 여덟 편은 32문항 중 22문항이 그랬다.
오답을 틀린 채로 늘려서 80문항 전부 길이로는 아무것도 알 수 없게 고쳤고, 검증이 다시 그렇게 되는 것을 막는다.

검증이 보는 것

- 모든 중국어 문장이 5급 누적 어휘 3,600어와 认读字 1,527자 안에 있는지
- 단락 배열의 연결마다 순서를 정하는 단서(`cue`)가 적혀 있는지. 비어 있으면 순서가 유일하지 않은 문항이라는 뜻이다
- 빈칸의 선택지 넷에 각각 왜 되고 왜 안 되는지(`note`)가 적혀 있는지
- 어순 문항의 `sentence` 가 `chunks` 를 이어 붙인 것과 맞는지
- 긴 지문의 `where`(근거 문장) 가 본문에 글자 그대로 있는지. 없으면 본문이 답하지 않는 문항이라는 뜻이다
- 긴 지문에서 정답이 혼자 가장 긴 보기가 아닌지. 그러면 읽지 않고 길이로 고를 수 있다
- 긴 지문의 보기 해설이 해석인지. '본문에' 로 시작하는 말이 들어 있으면 해석이 아니다
- 긴 지문의 주요 어휘가 여섯에서 열 개 사이이고, 모두 그 본문 안에 있는 단어인지
- 쓰기 점검 규칙이 적어 둔 예문(`bad`)을 실제로 잡는지, 고친 모양이 `good` 과 같은지

쓰기 점검 규칙은 한 가지를 더 본다. 레포 안에 있는 올바른 중국어 1,166개에 규칙을 전부 돌려서
한 건도 걸리지 않아야 한다. 한 건이라도 걸리면 맞는 표현을 틀렸다고 가르치는 규칙이라는 뜻이다.
처음 쓴 규칙 중 네 개가 여기서 걸렸다. 方便是方便, 开不了了, 一层、二层 같은 맞는 문장을 잡아서
고치거나 뺐다. 애매한 규칙은 아예 넣지 않는다. 틀린 교정을 외우는 쪽이 아무 말도 안 듣는 쪽보다 나쁘다.

고유명사처럼 어휘표 밖이어도 괜찮은 것은 `tools/whitelist.json` 에 이유와 함께 적는다.
`好不好` 안의 `好不` 처럼 실제로는 그 단어가 아닌 경우는 `tools/substring-ok.json` 에 적는다.

## 배포

`main` 에 푸시하면 끝이다. 깃허브 액션이 검증을 돌리고, `tools/pack.py` 로 올릴 폴더를
뽑아서 Pages 에 올린다. 검증이 통과하지 못하면 배포하지 않는다.

올리는 폴더에는 웹에 필요한 파일만 들어간다. `tools/` 는 빠진다.
`pack.py` 가 올릴 js 와 json 이 `sw.js` 의 오프라인 목록에 다 들어 있는지 본다.
빠지면 지하철에서만 틀어진다. 손으로 관리하면 반드시 빠뜨리는 목록이다.
`sw.js` 의 캐시 이름에는 문항 내용의 해시가 박혀서, 문항을 고치면 이미 깔린 기기도
새 파일을 받는다. 번호를 손으로 올릴 일이 없다.

손으로 폴더만 뽑아 보려면 이렇게 한다.

```bash
python tools/pack.py
```
